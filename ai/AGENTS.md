# AGENTS.md — Android Project Guidelines

## Роли

- **Тимлид** — принимает архитектурные и продуктовые решения, даёт финальный аппрув.
- **Агент** — предлагает решения, пишет код и объясняет трейдоффы только после аппрува.

---

## Главное правило: Plan → Approve → Execute

Перед любым изменением агент обязан:

1. Описать план: что делаем, какие файлы трогаем, зачем.
2. Дождаться явного аппрува: `ок`, `давай`, `делай`, `go`, `approve`.
3. Выполнять задачу пошагово.
4. Не делать ничего “заодно”.

Запрещено:

- писать код до аппрува;
- менять файлы вне согласованного скоупа;
- молча чинить найденные попутные проблемы.

Если план изменился — остановиться и пересогласовать.

---

## Архитектура

- Clean Architecture: `data`, `domain`, `presentation`.
- MVI + Unidirectional Data Flow.
- Single Source of Truth.
- Стек: Kotlin Multiplatform, Compose Multiplatform, Ktor, kotlinx.serialization, SQLDelight, Koin.

### Модули

При росте проекта:

- feature-модули: `:feature:login`, `:feature:dashboard`;
- core-модули: `:core:network`, `:core:ui`, `:core:database`.

Вынос в модуль — только после обсуждения с тимлидом.

---

## Kotlin-правила

- Официальный Kotlin Coding Conventions.
- Модели — `data class`.
- Состояния/события — `sealed class` / `sealed interface`.
- Не использовать `!!`.
- Предпочитать `val`.
- Extension-функции — только при реальном переиспользовании.

---

## Use Cases

- Один публичный метод: `operator fun invoke(...)`.
- Возвращают `Flow<Result<T>>` или `suspend fun -> Result<T>`.
- Не зависят от Android.

---

## Репозитории

- Интерфейс — в `domain`.
- Реализация — в `data`.
- DTO → Domain маппинг — только в `data`.

---

## Работа с файлами

- Не удалять файлы без явного согласования.
- Перед рефакторингом показать diff-план.
- Для новых файлов сначала показать структуру/сигнатуры, потом реализацию.
- Переименование/перемещение — отдельный аппрув.

---
